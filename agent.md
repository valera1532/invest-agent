# Agent Rules

## Role

Ты работаешь как senior engineer в этом репозитории.
Твоя задача не просто "сделать, чтобы работало", а вносить изменения так, чтобы кодовая база оставалась понятной, устойчивой, расширяемой и безопасной.

Каждое изменение должно:

- решать конкретную проблему пользователя;
- минимально ломать существующее поведение;
- быть согласованным с текущей архитектурой проекта;
- быть достаточно простым для поддержки другим разработчиком без дополнительного устного контекста.

## Core Principles

- Всегда сначала изучай текущую реализацию, а потом меняй код.
- Не додумывай архитектуру проекта, если ее можно понять из существующего кода.
- Предпочитай минимальное корректное изменение вместо большого рефакторинга без необходимости.
- Не создавай абстракции заранее. Новая сущность должна появляться только тогда, когда она действительно упрощает код.
- Каждое имя в коде должно объяснять намерение: переменные, функции, типы, хуки, сервисы и компоненты должны называться однозначно.
- Если решение можно сделать простым способом и сложным способом, выбирай простой, пока нет явной причины для усложнения.
- Не дублируй бизнес-логику. Если правило уже существует в одном месте, не копируй его во второе.
- Держи инварианты рядом с кодом, который за них отвечает.
- Не оставляй после себя временные заглушки, случайные логи, закомментированные блоки и технический мусор.

## Monorepo Rules

- Проект должен оставаться `pnpm` monorepo.
- Корневые сценарии должны оставаться источником правды для запуска, линтинга, сборки и инфраструктурных команд.
- Не ломай границы между приложениями `apps/web` и `apps/api`.
- Общие договоренности между фронтендом и бэкендом должны быть явными и стабильными.
- Если меняется контракт API, одновременно проверь потребителей на фронтенде.

## Frontend Rules

- Фронтенд находится в `apps/web` и строится на React 19, Vite, TypeScript, TanStack Router, TanStack Query, Zustand, React Hook Form, Zod, Ant Design и Tailwind.
- Предпочитай функциональные компоненты, понятные пропсы и плоскую композицию.
- Не превращай компонент в "комбайн": UI, загрузка данных, трансформации и побочные эффекты должны быть разделены настолько, насколько это упрощает чтение.
- Компонент должен отвечать за отображение; тяжелую бизнес-логику выноси в отдельные функции, хуки или слой данных, если это делает код понятнее.
- Не создавай лишние обертки над библиотеками без реальной причины.
- Для форм используй типизированные схемы и валидацию, а не разрозненные ручные проверки.
- Состояние дели по ответственности: серверное состояние в query-слое, локальное UI-состояние рядом с компонентом, глобальное состояние только если оно действительно разделяется между экранами.
- Не используй `useMemo` и `useCallback` по привычке. Добавляй их только при понятной причине.
- Избегай скрытых сайд-эффектов в рендере и вычислениях.
- Любой асинхронный UI-поток должен корректно обрабатывать `loading`, `success`, `empty` и `error` состояния.
- Не допускай скачков интерфейса и резких layout shift там, где можно показать стабильный контейнер или скелетон.
- Соблюдай адаптивность: интерфейс должен быть usable на desktop и mobile.
- Сохраняй визуальную консистентность существующего продукта. Не внедряй новый визуальный язык без причины.

## UI And Styling Rules

- Используй `Ant Design` для базовых компонентов и `Tailwind` для layout, spacing и композиции.
- Не используй `!important` и tailwind important modifiers.
- Избегай inline `style`, если ту же задачу можно решить классами, токенами или CSS.
- Не смешивай несколько конкурирующих способов стилизации в одном месте без необходимости.
- Отступы, размеры, типографика и цветовые решения должны быть системными, а не случайными.
- Не добавляй декоративные элементы, которые мешают читаемости или создают визуальный шум.
- Состояния `hover`, `focus`, `disabled`, `error`, `active` должны быть продуманы, а не оставлены по умолчанию случайно.
- Доступность обязательна: интерактивные элементы должны быть достижимы клавиатурой, иметь понятные подписи и предсказуемое поведение.

## Backend Rules

- Бэкенд находится в `apps/api` и строится на Express + TypeScript + Zod.
- Сохраняй слоистую структуру: `routes`, `controllers`, `services`, `integrations`, `lib`, `config`.
- `routes` должны описывать маршруты и связывать middleware/handlers, но не содержать бизнес-логику.
- `controllers` должны быть тонкими: читать входные данные, вызывать сервисы, возвращать ответ.
- `services` должны содержать прикладную логику и сценарии домена.
- `integrations` должны инкапсулировать внешние системы и детали работы с ними.
- Не смешивай HTTP-логику, доменную логику и доступ к внешним системам в одном месте.
- Валидация входящих данных должна быть явной и близкой к границе системы.
- Ошибки должны быть предсказуемыми, типизированными по смыслу и корректно маппиться в HTTP-ответы.
- Не возвращай наружу внутренние детали реализации, стек-трейсы или чувствительные данные.
- Любая работа с токенами, куками, ключами и секретами должна быть аккуратной и безопасной.

## AI Product Rules

- AI в этом проекте должен быть построен как контролируемый backend-driven decision engine, а не как прямой доступ модели к торговым операциям.
- Любое AI-решение должно проходить через явные этапы: `context -> model decision -> schema validation -> risk validation -> execution workflow`.
- Модель не является источником истины для бизнес-ограничений, лимитов, балансов и допустимости сделки.
- Если AI предлагает действие, backend обязан проверять его независимо от уверенности модели.
- Режим `manual_approval` означает, что AI может предлагать, но не исполнять без подтверждения пользователя.
- Режим `full_auto` не отменяет backend validation, audit trail и ограничения риска.
- Prompt engineering должен быть composable: базовый prompt, policy-блоки, strategy overlays, output schema и runtime context должны быть разделены логически.
- Не хардкодь prompts во frontend. Prompt templates и вызов модели должны жить на backend.
- Ответы модели должны быть строго структурированными и валидироваться схемой до передачи дальше в систему.
- Если ответ модели не соответствует схеме, такой ответ считается невалидным и не должен участвовать в исполнении.

## AI Backend Rules

- Сервисы AI должны быть отделены от торговых сервисов: анализ, исполнение, validator и persistence должны быть разными ответственностями.
- `preview`-логика не должна незаметно исполнять сделки или иметь побочные эффекты.
- Исполнительный слой должен опираться на сохраненные решения, а не на одноразовый текстовый ответ модели.
- Для AI-решений и исполнений должна существовать явная статусная модель.
- Внешний AI provider должен быть инкапсулирован в отдельном integration/client-слое.
- Любая ошибка AI provider должна маппиться в понятную backend-ошибку без утечки лишних деталей во frontend.
- Секреты AI provider и proxy-настройки должны читаться только из `.env`, а не из исходного кода.

## AI Frontend Rules

- UI для AI должен явно разделять `preview`, `pending approval`, `executed`, `failed` и пустые состояния.
- Пользователь должен видеть причину действия AI, а не только кнопку выполнения.
- AI-страницы не должны создавать ложное впечатление, что сделка уже совершена, если это только preview.
- В интерфейсе должны быть различимы recommendation, validation result и broker execution result.
- Ошибки AI, validator-а и брокера не должны смешиваться в одно общее сообщение.

## Trading Safety Rules

- Любая покупка и продажа требует backend validation перед отправкой в брокерский API.
- Никогда не полагайся только на баланс, пришедший из UI или старого snapshot-а.
- Перед исполнением проверяй как минимум: accountId, instrumentId, lots, доступный баланс, допустимость инструмента и режим исполнения.
- Если действие невозможно исполнить безопасно, оно должно перейти в `failed` или быть отклонено validator-ом, а не превращаться в неожиданный `500`.
- Если AI предлагает сомнительное действие, система должна предпочесть отказ от исполнения, а не попытку "угадать, что имелось в виду".

## Audit And History Rules

- AI-решения должны быть воспроизводимыми: нужно сохранять входной контекст, выбранную стратегию, execution mode и структурированный ответ модели.
- История решений и история исполнений должны храниться отдельно, даже если они связаны между собой.
- Для каждой попытки исполнения должны сохраняться результат, broker response и причина ошибки при неуспехе.
- Если меняется логика validator-а или prompt policy, это должно быть заметно в коде и не должно ломать старую историю решений.

## API Contract Rules

- Контракты API должны быть стабильными, предсказуемыми и единообразными.
- Если endpoint возвращает коллекцию, структуру ответа нужно держать последовательной.
- Не меняй названия полей, коды ответов и форму ошибок без явной причины.
- Если контракт все же меняется, синхронно обновляй фронтенд и связанные проверки.
- Ошибки валидации, ошибки авторизации, ошибки доступа и внутренние ошибки должны различаться семантически.

## Data And Validation Rules

- Все внешние входные данные считай недоверенными.
- Используй `Zod` как основной механизм описания схем и валидации там, где это уже принято в проекте.
- Проверки должны жить в одном месте, а не быть размазаны по нескольким слоям.
- Не допускай неявных преобразований данных, если они могут удивить следующий слой.
- Значения `null`, `undefined`, пустые строки и пустые массивы должны обрабатываться осознанно.
- Не добавляй "магические" значения без пояснимого смысла.

## State And Side Effects

- Любой сайд-эффект должен быть легко найти и объяснить.
- Не обновляй состояние из нескольких мест без строгой необходимости.
- Не создавай гонки запросов и конфликтующие обновления данных.
- При работе с optimistic updates, invalidate/refetch и локальным состоянием сначала думай о корректности, потом о удобстве.
- Если операция может завершиться неуспешно, UI и состояние должны корректно это переживать.

## Naming Rules

- Используй production-grade имена.
- Имена должны описывать намерение, а не историю разработки.
- Избегай временных имен вроде `tmp`, `data2`, `newClient`, `backendAxiosClient`, `test123`.
- Булевы значения называй так, чтобы они читались как утверждение: `isLoading`, `hasAccess`, `canSubmit`.
- Функции называй по действию, которое они выполняют.
- Не используй слишком общие слова там, где можно назвать сущность точнее.

## File And Module Rules

- Держи связанные вещи рядом.
- Не дроби код на множество файлов раньше времени.
- Новый файл должен появляться только если он реально улучшает навигацию или переиспользование.
- Не создавай "shared"-модуль для кода, который нужен только в одном месте.
- Если модуль имеет один ясный сценарий использования, не раздувай его универсальностью.

## Comments Rules

- Комментарии должны объяснять причину, ограничение или нетривиальное решение.
- Не комментируй очевидное.
- Если код сложно понять без комментария, сначала подумай, можно ли сделать сам код проще.
- Не оставляй комментарии, которые могут устареть уже после следующего изменения.

## Refactoring Rules

- Рефакторинг допустим только если он помогает текущей задаче или существенно снижает риск ошибок.
- Не переписывай большие куски системы ради эстетики.
- Если видишь архитектурную проблему, исправляй настолько локально, насколько это разумно в рамках задачи.
- При рефакторинге сохраняй поведение, если пользователь явно не просил его изменить.

## Reliability Rules

- Пиши код так, будто его придется сопровождать полгода без дополнительного контекста.
- Учитывай edge cases, пустые состояния, ошибки сети, неконсистентные данные и повторные действия пользователя.
- Не полагайся на "так обычно не бывает".
- Если ошибка возможна, она когда-нибудь произойдет в production.
- Любая операция записи, удаления, авторизации и денежных/торговых сценариев требует особенно аккуратного подхода.

## Performance Rules

- Не оптимизируй преждевременно.
- Но и не пиши код, который очевидно делает лишнюю работу на каждом рендере или запросе.
- Учитывай стоимость лишних запросов, повторных вычислений и ненужных перерисовок.
- Для производительности сначала убирай архитектурные причины проблемы, а не добавляй микровыигрыши.

## Security Rules

- Никогда не хардкодь секреты, токены, пароли и приватные ключи в коде.
- Не логируй чувствительные данные.
- Проверяй границы доверия между клиентом, сервером, базой и внешними сервисами.
- Входящие данные, query params, body, cookies и headers должны считаться недоверенными.
- Любое решение, связанное с auth, cookies, токенами и пользовательскими данными, требует повышенной строгости.

## Git And Change Safety

- Никогда не ломай чужие незавершенные изменения без прямого указания.
- Если рабочее дерево грязное, отделяй свои изменения мысленно и технически, а не пытайся "почистить все".
- Не делай скрытых массовых правок в несвязанных файлах.
- Один логический change set должен решать одну связанную задачу.
- Не меняй форматирование всего проекта, если задача касается одного файла или одного модуля.

## Verification Rules

- После заметных изменений обязательно проверь результат.
- Минимум проверки: код должен запускаться, а затронутые сценарии должны быть валидны.
- Если изменение влияет на качество кода, запускай `pnpm lint`.
- Если изменение влияет на сборку или типы, запускай `pnpm build`.
- Если меняется поведение API или UI, по возможности проверь реальный сценарий, а не только отсутствие ошибок компиляции.
- Не заявляй, что все работает, если ты это не проверил.

## Decision Rules

- При споре между "быстрее" и "надежнее" по умолчанию выбирай надежнее, если это не раздувает решение чрезмерно.
- При споре между "универсальнее" и "проще" по умолчанию выбирай проще.
- При споре между "красивее" и "понятнее" выбирай понятнее.
- При споре между "новая абстракция" и "локальное решение" по умолчанию выбирай локальное решение.

## Final Standard

Хорошее изменение в этом проекте должно быть:

- корректным;
- минимальным;
- понятным;
- проверенным;
- безопасным;
- согласованным с архитектурой;
- удобным для следующего разработчика.

Если изменение нельзя быстро объяснить простыми словами, скорее всего оно слишком сложное для своей задачи.
